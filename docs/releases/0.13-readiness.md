# IOsonata 0.13 release-readiness review

Review date: October 26, 2026 (Toronto).

Base: `f8c9eb234eea9284959a0ba09a80c43977d69f49`, the squash merge of PR 88.
Working branch: `release_0.13_readiness`.

Status: **not approved for tagging**. The repository integration and host-test
checks below passed after the listed fixes. Clean target builds, affected
hardware checks and the outstanding items below still need resolution.

## Fixes in this review

- Corrected 206 copied builder-directory references in 90 projects to use
  the project name declared by their own `.project` file. Build profile
  directory names are preserved.
- Corrected 208 linker-script references in 53 projects. These now point to
  the existing script of the same name in the shared MCU-family directory,
  or the existing local DFU source directory. No script contents or memory
  layouts changed. Already-valid script selections, including the nrfx UART
  examples' local scripts, are preserved.
- Removed the missing Icm20948Setup.c link from the nRF52832 MotionSensorDemo
  and its two exclusion entries. It was excluded in both configurations;
  this does not remove a compiled source.
- Repaired 14 stale links in Linux, Windows and RISC-V nRF54H20 projects:
  moved USB HID host paths, the Windows platform header, the renamed UC8151x
  header, and references to absent obsolete files. No driver source changed.
- Updated release notes for the PR 88 merge, confirmed RA4M1 USB results,
  the MSC layout/rebuild requirement, and the limited native TLS certificate
  profile. Repaired the RA4M1 documentation path and two installer guide links.

The project changes preserve compiler options, library selections, source
implementations and public APIs. They are metadata fixes, not evidence that
an incomplete port now works.

## Maintainer hardware validation: LPC54628

The following results are maintainer hardware validation and are separate from
the offline host and installer checks above. The build configuration and exact
tested firmware revision were not supplied, so these results are not a clean-build
claim for this review branch.

- CryptoTest: 101 passed, 0 failed, 0 skipped. AES-128/256, SHA-256/HMAC,
  CMAC/CCM/GCM, P-256/ECDH/ECDSA, bounds and rejection tests pass. The RNG
  reports a secure random generator and the included statistical checks pass.
  The benchmark timer is 1 MHz. P-256 mean time is 407999 us for the selected
  engine and 407998 us for the software reference. These nearly identical
  timings are not evidence of hardware crypto acceleration.
- Timer 0: the supplied continuous capture passes. Trigger 0 remains exactly
  100000 us, Trigger 1 remains exactly 1000000 us, and Trigger 2 remains exactly
  250000 us from Count 10100 through 13100 ms. Earlier irregular measurements
  occurred during semihosting and an explicitly confirmed debugger pause and
  are not treated as a timer-driver failure.
- UART PRBS at 1 Mbaud sustains a final average of 100044.59 bytes/s, approximately
  full 8N1 throughput. The counters remain fixed at drop 5 and out of frame 1
  through the supplied approximately 20 reporting intervals, with no additional
  errors. The cause of the initial counts is unproven, so this is recorded as a
  stable sustained run rather than an entirely error-free run.

## Installer review follow-up

Reviewed the Linux, macOS and Windows SDK clone scripts, development-tool
installers and library builders. The release branch fixes these confirmed issues:

- Linux deleted an existing checkout after a failed pull. It now stops and
  preserves the checkout so network failures or local changes cannot trigger
  automatic deletion.
- All three clone scripts replaced mismatched or incomplete pinned ST checkouts
  in normal mode. They now stop with the required version and recovery guidance.
  Explicit force mode still deletes and replaces repositories; save local work
  before using it.
- Windows Git failures were not checked. Clone, pull, sparse checkout and
  submodule failures now throw before success is reported.
- Development-tool installers retried arbitrary clone failures as if the
  no-build option were unsupported. They now stop and retain the failure log.
  Windows also used the wrong clone-script branch and an unsupported force
  argument; these now match the other platforms and the clone script's CLI.
- Library-build failures were suppressed by Unix callers and unchecked by
  Windows callers. Failures now propagate. Unix development-tool installers
  also pass their Eclipse installation path to the builder.
- Generated Makefile paths pointed to CMSIS/Include instead of CMSIS/Core/Include.
- Linux help/version requests could install packages before parsing arguments.
  Dependency installation now follows argument parsing, and required curl,
  unzip and (for the development-tool installer) Python checks are included.
  Clone mode validation and macOS missing-value checks now reject invalid input.
- Successive project builds overwrote earlier logs. All three builders now use
  unique log names; Windows also uses a unique workspace per project.

Validation: `python3 tests/installer/test_installers.py` passes six test methods
covering failed updates, pinned checkout preservation, explicit force failures,
matching pins, side-effect-free help/invalid arguments, and separate failure
logs. Clone behavior runs under Bash and Zsh on Linux; both Unix build functions
run with a failing mock IDE. All Installer shell scripts pass syntax checks with
their respective shells. Tests use temporary files and fake Git/IDE commands;
they do not download SDKs or modify the host installation.

Remaining release checks and limitations:

- PowerShell changes require Windows PowerShell 5.1 execution tests. No PowerShell
  runtime was available for this review.
- Run fresh install, existing-checkout update, custom-path install and interrupted
  download recovery on native Linux, macOS and Windows, then build a real SDK
  project. The offline tests do not establish native installation readiness.
- Standalone clone auto-build detection still looks for Eclipse and can skip
  an IOcomposer-only installation. The standalone builder supports IOcomposer
  and can be invoked directly.
- Most SDK repositories follow their default branches, and installers download
  the clone script from main. A release snapshot does not freeze these inputs.
  Release reproducibility needs a dependency/version policy.
- Download/extraction and optional IDAP-tool paths still need native failure
  testing, including archive integrity and external service availability.

The installer fixes remove confirmed data-loss and false-success paths, but
installer release sign-off remains pending the native installation matrix.

## IOcomposer installation ownership

The complete IOcomposer installation has moved into the three IOsonata
`install_iocdevtools_*` scripts. They install the Eclipse Embedded CDT runtime
at the final IOcomposer path, add the AI/UI plugins and branding, configure
SDK paths, build libraries and generate the external SDK index. Defaults are
`~/iocomposer` on Linux, `/Applications/IOcomposer.app` on macOS and
`%ProgramFiles%\IOcomposer` on Windows. SDK roots remain unchanged.

The website scripts are now thin launchers on the companion branch
`I-SYST/iocomposer.io:release_0.13_installer_handoff`. Merge IOsonata first, then
the website launchers. Deployment instructions and exact launcher copies are
in `Installer/website`. Neither main branch nor the live website was changed.

Both IOcomposer plugins are staged and checked before replacement. SDK path
preferences survive UI configuration, repeated runs retain one customization
hook, and normal macOS updates reuse the installed runtime. The clone scripts
now detect the default IOcomposer installation before the Eclipse fallback,
closing the default IOcomposer-only auto-build gap noted above.

Five additional offline regression methods cover plugin setup, repeatability,
failed downloads, invalid archives and launcher argument/status forwarding.
They pass alongside the six earlier installer regression methods. All shell
scripts pass syntax checks. Windows PowerShell and native macOS signing remain
unverified; the native installation matrix is still required for release sign-off.

## Firmware tools in the SDK Tools directory

All full installers now set up SRecord and pyOCD alongside IDAP-Link under
`Tools`: `Tools/SRecord`, `Tools/Python` (the pyOCD virtual environment) and
`Tools/IDAP-Link`. The clone scripts use the same IDAP-Link destination. IDE
project PATH preferences and generated Makefile variables expose the new tools.
Legacy tool directories remain untouched; the installer migrates only its
recognizable old global pyOCD symlink.

Linux/macOS use a native SRecord package and link the executables into the SDK
Tools directory, preserving package-managed shared libraries. macOS requires
Homebrew or MacPorts unless SRecord is already available. Windows downloads
the official portable SRecord 1.64 ZIP, checks its SHA256 before extraction and
verifies srec_cat execution. Python packages are installed only into the venv.
Uninstall removes managed Tools subdirectories, not native SRecord packages.

Three additional offline test methods verify venv-only pip calls, failure
propagation, SRecord command linking and repeated runs without self-links.
All 14 installer test methods and shell syntax checks pass. These use mocked
tools; native package downloads, Windows execution and hardware probe access
remain part of the required native installation validation.

## LLVM compiler installation

The full installers now provision one Clang/LLVM installation for Arm and
RISC-V under `Tools/LLVM`, alongside GCC. Linux uses distribution packages;
macOS uses Homebrew LLVM and the separately packaged LLD; Windows uses pinned,
SHA256-verified LLVM 23.1.4 x64/Arm64 administrative MSI extraction. Existing
project compiler defaults and GCC toolchain preferences remain unchanged.

Each installation must pass freestanding C/C++ compile, link and HEX-output
checks for Cortex-M4 and RV32IMAC. Explicit compiler/linker paths and target
options are exported in generated Makefile variables, with LLVM locations in
IDE project environment preferences. Complete LLVM firmware project profiles
and target runtime selection remain separate work.

The three additional offline test methods verify target-check invocation,
RISC-V failure propagation and missing-linker rejection. All 17 offline
installer test methods and shell syntax checks pass. No native Clang compiler
was available in the review environment: the tests use fake executables and
are not evidence of successful target compilation. Windows extraction and
native installation remain unverified until the platform installation matrix.

The Linux, macOS and Windows clone scripts install
`external/STM32CubeWBA` at `v1.10.0` and `external/stm32-mw-wpan` at `v2.10.0`.
The Cube tag's `Middlewares/ST/STM32_WPAN` gitlink is
`7e764835982f0a8b94fdd6b2b056d6e0afc4d1ba`, exactly the WPAN tag's commit.
WPAN is cloned separately at the location used by IOsonata projects.
Sparse checkout includes the common WPAN platform code, NUCLEO-WBA65RI BLE
p2pServer platform files and Utilities. No HAL or CMSIS submodules are downloaded.
The maintainer confirms IOsonata already compiles without HAL; the earlier

Existing-checkout acceptance requires the pinned tag and platform paths, with
no HAL or external CMSIS check. Incomplete checkouts remain preserved and require
attention; force mode remains explicitly destructive. Existing extra driver

External CMSIS include paths were removed from the WBA65 library project in the

Validation: installer regressions cover a complete platform checkout without
HAL or CMSIS, rejection of a HAL-only incomplete checkout, and clone commands
without driver downloads or submodule initialization under Bash and Zsh.
Shell syntax checks pass. Native Windows installation and a fresh WBA firmware
build were not run here; maintainer build evidence remains authoritative.

## Optional LLVM installation

LLVM is skipped by default on all platforms. Explicit --with-llvm (Unix) or
-WithLLVM (Windows) enables it; a failure is reported without blocking the
remaining setup. The final summary records its status. This avoids the reported
Homebrew Python dependency build failure on macOS 11 during default setup.
No compatible prebuilt macOS 11 LLVM replacement has been selected yet.

## IDAP-Link archive validation

All three installers now stage IDAP-Link updates before replacing an existing
installation and check for a nonempty IDAPnRFProg executable. Download,
extraction and missing-executable failures no longer report success. Linux and
macOS behavior is covered by the mocked offline failure/replacement test.
Windows now follows the same preserve-before-replace sequence, but native
PowerShell execution remains part of the outstanding platform matrix. Native
execution of IDAPnRFProg is not tested here.

## Managed Python restart behavior

Installer reruns now reuse a usable Python 3.9-or-newer interpreter already in
`Tools/Python` before requiring a separate host Python installation. Linux
dependency detection accepts that managed interpreter, macOS helper scripts use
it after setup, and Windows checks the managed interpreter before searching for
or installing another Python. A host Python with `venv` is still required when
the managed environment must be created. The existing Unix venv regression now
makes the host `python3` fail, so reuse of the managed environment is covered.
Native Windows execution remains part of the outstanding platform matrix.

## macOS 11 SRecord package path

The default macOS installer no longer permits Homebrew to fall back to building
SRecord from source. It prefers MacPorts when available; otherwise it queries
the current Homebrew formula metadata and installs only when an exact bottle is
published for the running macOS version and CPU. If there is no exact bottle,
setup stops with instructions to use MacPorts or provide `srec_cat` on PATH.

This matters for the maintainer's Intel macOS 11 host: the current Homebrew
SRecord formula does not publish an Intel Big Sur bottle, so a normal Homebrew
install would build from source together with its build dependencies. The
installer now avoids that path. A fresh macOS 11 installation still requires
MacPorts or an existing SRecord installation and remains native-unvalidated.

## Windows xPack download and extraction checks

The Windows xPack installer now uses a unique temporary directory for each
tool download, requires HTTP and 7-Zip success, and checks that the expected
nonempty executable is present before replacing an existing version directory.
Force updates keep the previous directory as a rollback copy until the staged
tool is installed. This also prevents a failed download from reusing a stale
fixed-name ZIP. Native PowerShell execution is still required for platform
validation.
